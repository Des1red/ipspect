# Changelog

**Version:** `v3.0.1`  
**Date:** 14 October 2026

## Nuclei Detection Request Database

* Integrated compatible **ProjectDiscovery Nuclei network detection templates** as an additional source of active TCP service-identification requests.

* Added an embedded request database under:

  ```text
  internal/database/data/requests/
  ```

  Template data is loaded through `internal/database/load/requests/` and is available without fetching templates during a scan.

* Added parsing of supported Nuclei TCP/network template fields into reusable probe definitions, including:

  * template ID and service classification;
  * TCP or TLS transport;
  * request payload and response read size;
  * suggested service ports;
  * response-matching conditions.

* Restricted template loading to supported, information-level service-detection templates. The loader requires recognized service/detection tags, a single independent request and input, supported static text or hex payloads, and compatible response matchers. Unsupported, dynamic, or vulnerability-oriented templates are not treated as general service probes.

* Kept the request database separate from **Rapid7 Recog**: Nuclei contributes probe payloads and template-specific response rules; Recog identifies recognizable products and protocols from observed responses.

## Evidence-Based Nuclei Request Selection

* Added `models.NucleiSearch` to centralize the information used when selecting additional detection requests:

  ```go
  type NucleiSearch struct {
      Target      string
      Port        int
      DBLookup    string
      Banner      string
      RawResponse []byte
      Headers     map[string][]string
  }
  ```

* Added `models.NewNucleiSearch()` to build an independent snapshot from the target and the relevant `PortDetail` fields. Raw-response bytes and header values are copied so the selection model does not modify the stored findings.

* Introduced `requests.ForEvidence()` to prioritize candidate probes using several sources of evidence rather than only the target port.

* Added initial scoring rules for request ordering:

  | Selection signal | Priority score |
  |---|---:|
  | Existing response matches a template's supported response conditions | +100 |
  | Normalized IANA service hint matches the template service | +40 |
  | Target port matches a template's suggested port | +10 |

  These are **relative ranking weights**, not detection-confidence percentages.

* Preserved stable ordering for equally ranked probes and continued considering templates associated with other ports. A service listening on an unexpected port is not excluded solely because of its port number.

* Retained the `ForPort()` entry point for compatibility while routing live Nuclei selection through the evidence-based API.

* Updated raw fingerprinting to create a `NucleiSearch` snapshot and attempt the resulting prioritized probe sequence.

* Kept early exit after a recognized response. If no probe identifies the service, the scanner may still exhaust its compatible request templates; the ranking does not impose a request limit.

## Response Recognition and Template Matching

* Extracted Nuclei response-condition evaluation into reusable `requests.MatchResponse()` logic, avoiding separate implementations of the same matching rules.

* Preserved supported word, binary, and regular-expression matchers, case-insensitive comparison, and `and`/`or` conditions.

* Updated the fingerprint analyzer to delegate Nuclei template matching to the shared matcher while retaining the existing fingerprint-result format and medium-confidence classification for successful template matches.

* Preserved the active response-analysis order:

  ```text
  Selected Nuclei request
           ↓
  IPSpect sends payload and reads response
           ↓
  Rapid7 Recog recognition
           ↓  (if no Recog match)
  Nuclei template response matcher
           ↓
  Record supported fingerprint or continue
  ```

* Maintained the separation between **request selection** and **service confirmation**: a favorable port, IANA name, or matching selection hint does not by itself establish the service identity.

## Centralized Service Name Normalization

* Introduced the shared service-name normalization package:

  ```text
  internal/service/normalize.go
  ```

* Consolidated service aliases used by Nuclei request ranking and final service resolution into one shared implementation.

* Preserved existing aliases while supporting additional equivalent service names, including registered names for DNS, HTTP, remote desktop, file sharing, and mail-related services.

* Updated service resolution to compare normalized names when deciding whether an observed fingerprint agrees with the IANA registration.

* Updated Nuclei selection to normalize both the IANA hint and candidate template service before comparing them.

* Kept the Nuclei template-tag whitelist independent of name normalization: determining whether a template is supported is a separate responsibility from comparing equivalent service names.

## Models and Fingerprinting Boundaries

* Split the shared models into purpose-specific files within the existing `models` package:

  ```text
  internal/models/
    scope.go       Target scope, port selection, and scan mode
    findings.go    Discovered hosts, ports, ARP data, and fingerprints
    nuclei.go      Evidence passed to Nuclei request selection
    recog.go       Evidence passed to Rapid7 Recog recognition
  ```

* Kept `models.INFO` and `models.TR` responsible for the requested scan scope, and `models.LOOT` responsible for accumulated findings. Existing model names and scanner data ownership remain intact.

* Added a dedicated `models.RecogEvidence` input containing captured banner, HTTP headers, and raw response bytes, with a constructor to copy the required evidence from `PortDetail`.

* Adapted passive and raw Recog recognition interfaces to use the focused evidence model rather than depending on an entire port finding. This is an input-boundary refactor; it does not introduce new Recog signatures or protocol support.

* Kept fingerprint enrichment and final service resolution separate from request selection. Recognized service/product information continues to be recorded in the existing fingerprint and port findings.

## Database Documentation

* Added `DATABASES.md` to explain the distinct roles of **IANA**, **Rapid7 Recog**, and **ProjectDiscovery Nuclei** in IPSpect.

* Documented how registered-port hints, captured responses, active requests, fingerprint matchers, and final service resolution connect.

* Kept the documentation independent of exact database counts, bundled fingerprint categories, and protocol-template inventories so those sources can evolve without changing the overall architecture description.

## Regression Tests and Runtime Validation

* Added selection tests covering conflicting clues, including a nonstandard port, a different IANA service hint, and response evidence favoring another template. The most strongly supported request is prioritized without removing fallback candidates.

* Confirmed the repository built and existing tests passed with:

  ```bash
  go test ./...
  ```

* Confirmed focused race and repeat tests passed during Nuclei-selector integration:

  ```bash
  go test -race ./internal/database/... ./internal/scanner/tcp/enrich/...
  go test -count=20 ./internal/database/load/requests/...
  ```

* Ran a full-range TCP scan against a local router using the updated source and compared the output with an installed IPSpect binary. Both runs identified the same **six open ports** and produced the same service and product identifications:

  ```text
  22     SSH / Dropbear
  23     Unknown (Telnet negotiation bytes retained)
  53     DNS
  80     HTTP
  1900   HTTP / libupnp
  7547   HTTP / TR-069 server
  ```

* The updated-source run classified all **65,535 TCP ports** and reported **zero unclassified operations**. The installed-binary run also reported complete outcome accounting, with one port classified as filtered instead of closed.

* The two runs recorded different retransmission counts and fingerprinting durations. These observations do **not** establish a speed improvement attributable to Nuclei selection; live network conditions and other scan activity can affect results.

* The reported automated tests and router comparison validate the Nuclei-selection work. A separate post-refactor runtime result for the focused Recog input model has not yet been documented.

## Current Service Identification Flow

```text
Open TCP port
       ↓
IANA registration lookup
       ↓
Initial banner and response collection
       ↓
Built-in passive recognition + Rapid7 Recog
       ↓
Dedicated protocol probes when needed
       ↓
Unidentified? Build NucleiSearch
       ↓
Rank compatible Nuclei detection requests
  ├── existing response evidence
  ├── normalized IANA service hint
  └── suggested port
       ↓
IPSpect sends selected request
       ↓
Rapid7 Recog → Nuclei response matcher
       ↓
Record fingerprint and supporting evidence
       ↓
Final service resolution
       ↓
Terminal results / Markdown report
```

The stages are conditional: once usable evidence identifies a service, IPSpect does not need to run every subsequent probe.

## Limitations

* Nuclei prioritization is heuristic and does not guarantee that the first payload is appropriate or that a service will be identified.
* The active request database accepts only templates compatible with the supported detection format; it does not execute arbitrary Nuclei workflows.
* An unknown service may still receive several active requests. No separate probe budget or service-specific request limit is enforced by the selector.
* Recog detection remains limited by the supported response formats and bundled fingerprint data. Unrecognized binary responses may remain unknown even when the registered port suggests a likely service.
* Passing tests and matching results on one router do not guarantee identical behavior or detection accuracy on other networks.

Only scan systems and networks you own or are explicitly authorized to assess.
